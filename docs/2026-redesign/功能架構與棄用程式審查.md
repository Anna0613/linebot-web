# Botlyn 功能、架構與棄用程式審查

2026-11-27，審查版本 `feat/cloudflare-nas-inbox` 的 `01050c4e`。資料從空白環境開始。本次檢查 Git 版本、本機編譯與隔離整合測試。下文的「有入口」指程式可達；正式流量、NAS 延遲、真實模型品質及 LINE 派送尚未實測。

## 此分支的執行結果

- 已移除原審查列出的 30 個孤立前端模組、舊建置外掛、重複的積木驗證邏輯及舊資料搬移腳本。實際聊天與流程重播共用的 Flex 預覽保留。前端新增入口可達性測試，每次測試會走訪 React 入口及瀏覽器 Worker。
- 已修復乾淨 checkout 的 motion 模組與型別檢查。Service Worker 僅快取帶內容雜湊的公開 JS/CSS，更新時會清除舊版應用的快取。意見回饋表單會寫入 PostgreSQL。
- 啟用 PG 旗標時，好友、收件匣、人工單發、指定好友廣播，以及本地報表使用同一份對話紀錄。全體廣播另存一筆派送意圖。FastAPI 啟動跳過 Redis、MongoDB 與 MinIO 預熱。資料庫從空白建立。[本機驗收](../../worker/README.md)
- 正式 AI 自動回覆、流程執行、聊天附件及圖文選單媒體仍需驗收；關閉 PG 旗標的路徑仍屬現行服務。下列發現及數量保留為改動前基準。

## 建議的架構取捨

1. **保留 React/Vite。** Workers Static Assets 能供應現有 SPA；把 `/api/*`、Webhook、WebSocket 路徑交給對應處理器，其他頁面支援深連結。現有工作區與畫布主要需要互動，改採 SSR 增加的移植成本沒有對應到已知功能需求。[Static Assets](https://developers.cloudflare.com/workers/static-assets/)
2. **NAS PostgreSQL 作為新系統唯一的業務資料庫。** 同一筆交易可處理入站唯一鍵、對話序號、接手版本及待派送紀錄。目標連線為 Worker → Hyperdrive → TCP VPC Service → Tunnel → NAS Docker PostgreSQL。NAS 負責保存、備份與還原；需量測真實往返延遲。首版保持客服授權與接手讀取的新鮮度。Queues 在 NAS 短暫離線期間緩衝入站；照其至少一次投遞語意保留資料庫去重。[Hyperdrive 私網連線](https://developers.cloudflare.com/hyperdrive/configuration/connect-to-private-database-vpc/) · [Queues 投遞語意](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)
3. **客服工作先用 PG + Queues；文件用 R2。** 客服送出、模型任務、檔案發布可在交易內留下待辦，再交給消費者。現在每次 tick 至多領一份待發布文件和一件草稿，本機每三秒觸發，尚未代表尖峰吞吐。優先讓新工作喚醒消費者，保留定期補撿與重試。大型檔案再改為受權上傳 R2，減少 PG 暫存原檔的負擔。五秒輪詢能符合第一版時效時，繼續使用；跨分頁即時接手若有明確延遲目標，再評估 Durable Objects。[Worker 排程](../../worker/src/index.ts) · [R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)
4. **保留薄層 TypeScript agent loop，使用 Workers AI。** 現階段需要的是 Bot 範圍內可授權、可定位原文的工具，以及派送前的控制權檢查。先以人工標註的新對話測引用正確率、缺證移交率、P95 延遲與每案成本。若客服流程真的要跨小時等待人工核可或持久恢復，再比較 Workflows 或 Agents SDK。若實測關鍵字找不到足夠多的正確段落，可先比較 PG 內索引，將額外服務留給量測結果決定。[Workers AI 工具呼叫](https://developers.cloudflare.com/workers-ai/features/function-calling/) · [Workflows](https://developers.cloudflare.com/workflows/) · [Agents SDK](https://developers.cloudflare.com/agents/)
5. **把 FastAPI 保留為過渡實作。** 現在啟動仍初始化 Mongo、Redis、MinIO 與背景服務，PG 旗標只增加收件匣路由，其他路由照常掛載。近期可讓新工作區只啟用所需的路由及服務，再把帳號、編輯器與營運操作逐批接到 Worker。PDF/DOCX 解析是否保留 Python，由繁中文件解析正確率和維運成本決定。新系統驗收採獨立資料庫與新物件空間。[FastAPI 啟動](../../backend/app/main.py) · [文件解析](../../backend/app/services/knowledge/source_publication.py)

### 可選的後端部署方式

| 方案 | 適用情況 | 本案代價 |
|---|---|---|
| Worker 收件及業務 API，NAS 只承擔 PG 和 Tunnel | 長期目標。相同資料契約可服務收件、編輯器與報表，驗簽、入列及模型在 Cloudflare 執行。 | 須移植登入、業務路由、正式執行器及派送，並驗證跨網路交易延遲。 |
| Worker 負責前端、入站與 AI，FastAPI 暫與 PG 同在 NAS | 短期替代。可先讓既有管理頁改讀同一 PG，以較小改動取得完整客服流程；複雜 SQL 與解析留在資料庫旁。 | NAS 離線時管理 API 暫停，即使 Worker 仍能入列；管理服務、依賴及備份演練仍要自行維護。 |

以目前功能覆蓋率，先採第二種方式接通新資料，再逐個業務移向第一種，能在每階段用同一個新 Bot 驗收。若日後 NAS 的可用率成為主要限制，再討論資料庫託管；目前缺乏量測支持更換 PostgreSQL。

## 驗收順序

先恢復乾淨建置、有效型別檢查及私人快取隔離。接著用一個新 Bot 驗證「第一則 LINE 訊息 → 兩頁顯示相同對話 → 接手 → 人工回覆 → 報表」，再補上文件、流程與 Flex 的發布和版本重播。最後以缺少 Mongo、Redis、MinIO 和舊模型金鑰的環境跑主要任務，通過後才從新系統相依項移除它們。前端孤立元件可獨立分批清理。

本次執行 Worker TypeScript 檢查、4 個 Node 測試及其中啟動的 2 個 Python 測試，均通過。涵蓋隔離 PostgreSQL、Miniflare、收件去重與中斷復原、文件版本、草稿、接手及測試版。真實 LINE 派送、遠端 Workers AI、NAS／Tunnel 故障及外部 API 使用量仍待整合驗收。
